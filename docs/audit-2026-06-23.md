# Gitwire + Gitwire Pro — Comprehensive Deep-Dive Audit

**Audit date:** 2026-06-23
**Scope:** `plugins/gitwire/` (free, v1.0.0) and `plugins/gitwire-pro/` (Pro, v1.0.0)

---

## Executive Summary

| Dimension | Score |
|---|---|
| **Overall Quality** | 71 / 100 |

| **Database** | 71 / 100 |

**Verdict: Controlled Beta.** The install/backup/rollback pipeline and the Pro encryption architecture are well thought-through. However, three issues block a stable release: a 7-char SHA truncation that silently corrupts update detection, a log file that is publicly readable on Nginx, and AES credentials tied to `wp_salt('auth')` so that any key rotation or site migration silently drops all private connections with no actionable error. The free plugin's REST class is a 2,476-line god class that makes testing impossible. Test coverage is under 5%.

## Critical Issues

### CRIT-1 — 7-Character SHA Stored in VARCHAR(40) Columns

**Free / `includes/class-github-api.php`**

`get_commits()` truncates every SHA to 7 characters:
```php
'sha' => substr( $c['sha'], 0, 7 ),
```

Every downstream code path (`store_head()`, `set_head()`, `run_auto_updates()`) stores that 7-char value into `head` and `remote_head`, which the schema declares `VARCHAR(40)`. The `update_available` flag is computed as `$remote_head !== $rec['head']`. Two commits with the same 7-char prefix — plausible in a long-running busy repository — will never trigger an update. The display shows "up to date" permanently. The schema column declaration is also misleading: anything that reads `VARCHAR(40)` will assume a full SHA and behave incorrectly on partial comparison.

**Fix:** Remove the `substr` in `get_commits()`. Store full 40-char SHAs everywhere. Truncate to 7 chars only at render time in the JS layer. Bump `Schema::DB_VERSION` and add a data fix in `Schema::install()` to zero out existing short SHAs so they are re-fetched.

---

### CRIT-2 — Activity Log Is Publicly Readable on Nginx

**Free / `includes/class-logger.php`**

```php
file_put_contents( $htaccess, 'Deny from all' );
```

The log lives at `wp-content/uploads/gitwire/activity.log`. On Nginx (the majority of modern VPS and cloud WordPress stacks), `.htaccess` is never parsed. Any visitor can fetch the raw log file directly. The log contains: WordPress usernames of every admin who performed an action, Git repository names (owner/repo), file paths from error messages, and failure details that may expose internal infrastructure names.

**Fix:** Move the log file outside the web root — `WP_CONTENT_DIR . '/gitwire-logs/activity.log'` is not web-served on any server. If uploads-relative placement is kept, add a `.php` wrapper that checks authentication before streaming, and document the Nginx `deny` rule requirement explicitly in the plugin description.

---

### CRIT-3 — AES Encryption Key Tied to `wp_salt('auth')` With Silent Failure

**Pro / `includes/class-connections.php`**

```php
$key = substr( hash( 'sha256', wp_salt( 'auth' ), true ), 0, 32 );
```

The encryption key is derived solely from `wp_salt('auth')`. This creates two production-breaking scenarios:

1. **Key rotation:** WordPress security guides recommend rotating `AUTH_KEY` and `AUTH_SALT` after a breach. Doing so changes the derived encryption key. Every private connection's credentials become undecryptable. `decrypt()` returns `''`, `get_credentials()` returns `[]`, and the installer fails silently with an API auth error — not "encryption key changed, reconnect." The user sees random install failures with no path to fix them other than re-entering all tokens.

2. **Site migration:** Migrating from staging to production (or restoring from backup to a new server) typically involves copying the database but generating new `wp-config.php` secrets. Same result: all tokens silently become invalid.

There is no version field on the encrypted blob, no migration path, and no error message distinguishing decryption failure from invalid credentials.

**Fix:** Store an HMAC of the current key alongside the ciphertext to detect key mismatch specifically. On decryption failure, return a typed error (`WP_Error('key_mismatch', ...)`) rather than an empty array, and surface "Reconnection required" in the admin UI. Separately, consider storing a per-connection salt that derives the actual AES key — this makes the blob resistant to bulk decryption even with the `wp_salt` value known.

### CRIT-4 — SSRF via GitLab URL — DNS Rebinding Not Mitigated

**Free / `includes/helper/class-settings.php`**

`is_allowed_gitlab_url()` validates the URL at storage time only. It correctly blocks literal private IPs and `localhost`, but:

- **IPv6 loopback `::1`** is not blocked.
- **Internal DNS names** (`redis.internal`, `db.local`, `metadata.google.internal`) are accepted — they don't parse as IP addresses.
- **DNS rebinding:** A domain can resolve to a public IP during validation, then switch to a private IP before the next `wp_remote_get()` call.

The validation runs once on `POST /settings`. All subsequent API calls to that GitLab URL are made without re-checking the resolved address.

**Fix:** Re-resolve and validate the IP at API call time inside the GitLab API client, not only at storage time. Block `::1` explicitly in `is_allowed_gitlab_url()`. Block the AWS/GCP/Azure metadata service IP ranges (`169.254.169.254`, `fd00:ec2::254`). Internal DNS hostnames should also be blocked — check if `gethostbyname()` resolves to a private range after parsing.

## High Priority

### HIGH-1 — N+1 Queries in `Connections::hydrate()` for GitLab

**Pro / `includes/class-connections.php`**

`all()` fetches all connections, then calls `hydrate()` on each GitLab row, which issues a separate `SELECT` to `gitwire_connection_meta` for `gitlab_url`. Five GitLab connections = 6 queries. This is called from `get_public_list()`, `get_credentials_for_provider()`, and `refresh_all_connections()`, all of which run on admin page load.

**Fix:** Rewrite `all()` to LEFT JOIN `gitwire_connection_meta` on `meta_key = 'gitlab_url'` for all rows in one query. Remove `hydrate()` and merge `gitlab_url` inline.

---

### HIGH-2 — License Gate Is a No-Op

**Pro / `includes/class-rest.php`**

`activate_license()` stores any non-empty string as an active license. No remote validation is performed. No Pro endpoint or feature checks `get_license_status()` before executing. The `/connections` CRUD works identically with `active: false`. The license system is a UI element that gates nothing.

This is either intentional (EDD/Freemius integration pending) or an oversight. Either way, it should either be wired up or clearly marked as a future stub so code reviewers don't mistake it for functioning DRM.

---

### HIGH-3 — `class-rest.php` (Free) Is a 2,476-Line God Class

**Free / `includes/class-rest.php`**

Route registration, repo listing, type detection, installation orchestration, branch switching, activation, deactivation, log management, public connections, settings, and profile caching are all in a single class. There is no way to unit-test any single route handler without bootstrapping the entire class.

**Recommended split:**
- `REST_Settings` — `/settings` GET/POST
- `REST_Repositories` — browse, detect, resolve, branches
- `REST_Installer` — install, switch, activate, deactivate, remove, untrack, auto-update
- `REST_Connections` — public connections CRUD
- `REST_Logs` — log read/clear
- `REST_Router` — only `register_routes()`, delegates to the above

---

### HIGH-4 — Missing Scope Check in `detect_batch()` and `get_branches()`

**Free / `includes/class-rest.php`**

`install()` correctly validates connection scope:
```php
if ( $conn && 'all' !== $db_scope && $db_scope !== (string) get_current_user_id() ) {
    return new \WP_Error( 'forbidden', … );
}
```

`detect_batch()` and `get_branches()` both accept a `connection_id` from the request body and call `make_api()` without any scope check. A multi-admin site where Admin A has a user-scoped private connection can have Admin B enumerate Admin A's private repositories by passing Admin A's connection ID to either endpoint.

**Fix:** Extract the scope check from `install()` into a reusable `self::assert_connection_scope( $id ): ?WP_Error` and call it in every endpoint that accepts a `connection_id`.

---

### HIGH-5 — No Atomic Lock for Concurrent Installs

**Free / `includes/class-installer.php`**

Install sequence:
1. Check if `$install_path` is a directory
2. Rename it to backup path
3. Extract new files

Steps 1 and 2 are not atomic. Two concurrent REST calls to install the same repo will both pass step 1 and race on step 2. The loser gets a rename error and leaves the filesystem in an undefined state while the winner proceeds over what it believes is a clean directory.

**Fix:** Before step 1, acquire a transient-based lock keyed on `gitwire_lock_{provider}_{full_name}` using `wp_cache_add()` (which is atomic on Memcached/Redis) with a 5-minute TTL. Release it in a `finally` block.

---

### HIGH-6 — `detect_batch()` Makes Up to 300 Synchronous HTTP Calls Per Request

**Free / `includes/class-rest.php`**

`detect_batch()` accepts up to 50 repositories. Each detection call makes one `get_root_contents()` call plus up to 5 file-read calls = up to 6 HTTP calls per repo. 50 repos × 6 calls = 300 outbound HTTP requests in a single synchronous REST response. PHP default timeout of 30s means this fails routinely at 10+ repos per batch.

**Fix:** Reduce the batch limit to 10 with pagination, or queue detections as a background job returning a cursor the client polls.

---

### HIGH-7 — `sync_installed()` Makes N Synchronous API Calls

**Free / `includes/class-rest.php`**

For each installed repo without a `head` or with a potentially stale `remote_head`, `sync_installed()` calls `api->get_commits()` inline. Ten installations = up to 10 HTTP calls before the REST response returns. This is called on the Gitwire admin page load.

**Fix:** Move remote-head polling entirely to the `gitwire_maintenance` cron event. The REST sync endpoint should return only what is currently in the database.

---

### HIGH-8 — `Admin::enqueue()` Runs Synchronous Business Logic

**Free / `includes/class-admin.php`**

On every Gitwire admin page load, `enqueue()`:
1. Calls `REST::get_installed()` → DB query + filesystem `is_dir()` stat on every install path
2. Reads and deletes `gitwire_pending_message` → two DB writes

The pending message read-then-delete is also non-idempotent: rapid back/forward navigation can delete the message before the first page render completes its JS boot.

**Fix:** Serve the SPA with minimal boot data (installed records only, no stat check). Move orphan detection and pending-message consumption to a dedicated REST call on app boot.

---

### HIGH-9 — `Logger` Reads the Entire Log File Into Memory

**Free / `includes/class-logger.php`**

`get_entries()` and `trim_old_entries()` both do `file_get_contents( $this->log_file )`. On a 30-day retention window with frequent deployments, the log file will grow to several megabytes. Reading it entirely into memory on every log-view or trim is a PHP memory exhaustion risk.

**Fix:** Implement streaming with `SplFileObject`. For `get_entries()`, stream from the end of the file. For `trim_old_entries()`, write to a temp file atomically and `rename()` it into place.

---

### HIGH-10 — Auto-update Cron Makes Unbounded API Calls Without Rate-Limit Awareness

**Free / `includes/class-installer.php`**

`run_auto_updates()` makes one `get_commits()` call per installed repo every cron cycle. GitHub's unauthenticated rate limit is 60 req/hr per IP. A site managing 30+ repos on a halfhourly cron hits the ceiling. There is no `X-RateLimit-Remaining` check; failed calls are logged but the cron re-runs on schedule regardless.

**Fix:** Cache `X-RateLimit-Remaining` from every API response in a transient per connection. Check before each cron call and skip the cycle if remaining is below a threshold.

## Medium Priority

### MED-1 — `Connections::all()` Has No Request-Scope Cache

**Pro / `includes/class-connections.php`**

`all()` queries the database on every call. Called from `get_public_list()`, `get_credentials_for_provider()`, and `refresh_all_connections()`. Fix: add `private static ?array $cache = null;` guard.

---

### MED-2 — `Connection_Resolver::all_rows()` Has No Request-Scope Cache

**Free / `includes/class-connection-resolver.php`**

Called from `install()`, `annotate_installed()`, `build_repo_list()`, `get_repos()`, and `sync_installed()` — each is a separate DB query for the same data within a single request. Same fix pattern.

---

### MED-3 — `Settings::get_raw()` Has No Request-Scope Cache

**Free / `includes/helper/class-settings.php`**

Multiple callers per request each call `get_raw()` and unpack the full options array independently.

```php
private static ?array $cache = null;
public static function get_raw(): array {
    self::$cache ??= (array) get_option( 'gitwire_settings', [] );
    return self::$cache;
}
```

---

### MED-4 — `gravatarFallback()` Generates Invalid Gravatar URLs

**Pro / `src/components/connections-section.js`**

Uses DJB2 hash of the identifier. Gravatar requires an MD5 hash of the lowercase email address. The generated URL always serves the default identicon.

**Fix:** Use MD5 on the identifier, or drop the fallback and rely on the provider avatar URL alone.

---

### MED-5 — `upsert()` Cannot Clear a GitLab Instance URL After It's Set

**Pro / `includes/class-connections.php`**

```php
if ( 'gitlab' === $provider && isset( $data['credentials']['gitlab_url'] ) ) {
    $wpdb->replace( self::meta_table(), … );
}
```

`isset()` on an empty string is `true`, so an empty `gitlab_url` does replace — but if the key is absent entirely (e.g., the caller omits it on edit), the old URL persists. More importantly, there is no path to delete the meta row; only replace. Change to `array_key_exists()` and handle the empty-string case with `$wpdb->delete()`.

---

### MED-6 — Duplicate Self-Heal Code in `activate()` and `deactivate()`

**Free / `includes/class-installer.php`**

The "re-scan when `plugin_file` is missing" block is copy-pasted verbatim in both methods. Extract to `private static function heal_plugin_file( array $rec ): ?string`.

---

### MED-7 — TOCTOU Race in `save_installed_record()`

**Free / `includes/class-installer.php`**

A pre-SELECT reads `installed_at` and `head` before the INSERT ON DUPLICATE KEY UPDATE. Between the two queries, another process can INSERT the same row, making the pre-fetched `installed_at` stale.

**Fix:** Use `INSERT ... ON DUPLICATE KEY UPDATE installed_at = COALESCE(installed_at, VALUES(installed_at))` to remove the pre-read entirely.

---

### MED-8 — `label_managed_plugins()` Mutates Plugin Name in `all_plugins` Filter

**Free / `includes/class-admin.php`**

```php
$all_plugins[ $file ]['Name'] .= ' [Gitwire]';
```

This appends to the name used for plugin comparison by WP-CLI, other plugins, and `plugin_basename()` lookups. Annotate via `plugin_action_links` instead.

---

### MED-9 — No `plugin_action_links` Hook

No "Settings" link appears in the plugins list table for either Gitwire or Gitwire Pro. Standard WP.org practice; reviewers will note it.

---

### MED-10 — Uninstall Does Not Clean `gitwire_detection_cursor` or Backup Directories

**Free / `uninstall.php`**

`gitwire_detection_cursor` (created in `cron_refresh_repo_types()`) is not deleted. Any `--gitwire-bak-*` or `--gitwire-failed-*` directories left by failed installs are also not cleaned up.

---

### MED-11 — Background Detection Cursor Doesn't Reset After Full Table Scan

**Free / `includes/class-repo-cache.php`**

The cursor resets to `0` only when `$untyped` is empty at the current offset. If repos are deleted between runs the cursor can skip past the end of the table, leaving newly inserted rows undetected until an accidental wraparound.

**Fix:** Reset to `0` whenever `count($untyped) === 0` regardless of cursor value.

---

### MED-12 — Missing Indexes on High-Traffic Query Paths

| Table | Missing Index | Query at risk |
|---|---|---|
| `gitwire_repositories` | `(connection_id, last_activity_at)` | Stale-row cleanup DELETE in `refresh_repo_lists()` |
| `gitwire_installations` | `(connection_id, type)` | Pro delete cascade lookups |
| `gitwire_connection_meta` | `(meta_key)` | GitLab URL bulk fetch across all connections |

```sql
ALTER TABLE gitwire_repositories
    ADD KEY conn_last_activity (connection_id, last_activity_at);

ALTER TABLE gitwire_installations
    ADD KEY conn_type (connection_id, type);

ALTER TABLE gitwire_connection_meta
    ADD KEY meta_key_idx (meta_key);
```

---

### MED-13 — `@since 3.0.0` in a v1.0.0 Plugin

**Free / `includes/class-connection-resolver.php`**

Carried over from an older codebase. Fix to `@since 1.0.0`.

---

### MED-14 — Pro `src/store.js` Is Not Concurrency-Safe

`setConnections()` and `setProfiles()` mutate a plain module-level object. Concurrent async operations (the `useEffect` on mount tests every connection) can interleave, with one `setProfiles()` call overwriting another's result.

**Fix:** Use `@wordpress/data` for a Redux-backed store with atomic actions.

## Nice-to-Have

### NTH-1 — Silent Catch on Background Connection Verification

**Pro / `src/components/connections-section.js`**

Empty `catch` block on connection test calls swallows network errors and auth failures. At minimum, update the profile state with an error flag so the UI shows a warning indicator instead of a stale "Connected" badge.

---

### NTH-2 — `Connections::to_public()` Decrypts on Every List Call

**Pro / `includes/class-connections.php`**

`to_public()` calls `decrypt()` on every connection record just to check `token_set`. Use `!empty($conn['credentials'])` for the boolean check; defer decryption to when the actual preview is needed.

---

### NTH-3 — No Webhook Endpoint

Neither plugin supports inbound webhooks. Users must trigger updates manually or wait for cron. A signed HMAC webhook would make Gitwire dramatically more useful in CI/CD pipelines.

---

### NTH-4 — PHP 8.1+ Features Underused

The plugins declare `Requires PHP: 8.1` but don't use constructor property promotion, `readonly` properties, or enums. Auto-update states (`'disabled'`, `'current'`, `'any'`) and log levels (`'activity'`, `'error'`) are natural candidates for `enum`.

---

### NTH-5 — No WP-Cron Health Check

If WP-Cron is disabled (common on high-traffic sites using system cron), no cache refresh, log trim, remote-head poll, or auto-update job fires. No notice or fallback informs the admin.

## Database Review

### Schema Design

Five tables. Overall design is solid:

- `gitwire_connections`: unified public/private store — `credentials IS NULL` for public is a clean approach
- `gitwire_connection_meta`: EAV for per-connection config; acceptable for low-cardinality keys like `gitlab_url` and profile cache
- `gitwire_installations`: correct compound UNIQUE KEY on `(provider, full_name)`
- `gitwire_commits`: correct compound PK on `(installation_id, branch)`, MEDIUMTEXT is appropriate for commit JSON
- `gitwire_repositories`: compound PK on `(connection_id, full_name)` is correct; `updated_at`-based stale-row cleanup is sound

**One fundamental design issue:** `head VARCHAR(40)` and `remote_head VARCHAR(40)` store 7-char SHAs. Must be fixed with a schema version bump and data migration.

### Scalability by Row Count

| Table | 1K rows | 10K rows | 100K rows | Bottleneck |
|---|---|---|---|---|
| `gitwire_installations` | Fine | Fine | Slow | `SELECT *` no-LIMIT; missing covering index on `connection_id` |
| `gitwire_repositories` | Fine | Noticeable | 200ms+ | Missing `(connection_id, last_activity_at)` for cleanup DELETE |
| `gitwire_connection_meta` | Fine | Fine | Fine | N+1 pattern in Pro `hydrate()` |

## Final Verdict

### Production-ready?

**No — Late Beta.** The installer architecture, fatal-error recovery, and Pro's hook-based extension model are production-quality work. The AES encryption design is thoughtful. But CRIT-1 (SHA) and CRIT-3 (key derivation) are data integrity and reliability failures that appear in real-world use, not edge cases. CRIT-2 (log file) is a privacy failure on the majority of modern WP stacks.

### WordPress.org suitable (free plugin)?

**Not yet.** Blockers: log file exposure on Nginx (CRIT-2), missing `plugin_action_links`, `label_managed_plugins()` mutating the plugin name in the filter. Test coverage should at minimum include installer, error handler, and REST endpoint smoke tests before submission.
